# wyyard 验证与收尾

授权、任务范围和完成标准统一遵循根目录 AGENTS.md。本 skill 决定怎么验证，不增加批准环节。

## 按影响选择检查

先看本次 diff、相关依赖和已有测试。使用项目现有依赖；以下命令从对应目录执行。

| 改动 | 默认验证 |
|---|---|
| 仅文档、提示词、Skills、静态预览 | 差异、引用/语法与实际展示（适用时）；不跑应用构建/数据库测试 |
| frontend/ 源码 | npm run build（当前含 tsc -b）；可先用类型检查定位问题，但同一版本已通过 build 不强制再跑一遍 tsc |
| backend/ 局部业务 | .venv/bin/python -m pytest 对应测试 + .venv/bin/ruff check 修改的 Python 文件 |
| 鉴权、扣卡/退费、共享持久化等高影响逻辑 | 对应回归 + 必要跨模块集成测试；共享影响难以界定、发布前或用户要求全量时运行完整 pytest |
| 小程序源码 | 修改 JS 的 node --check、JSON 解析、页面/组件注册和接口调用核对；可用时微信开发者工具编译并检查关键交互，不以 PC build 替代 |
| 准备提交源码 | 上述对应检查 + bash scripts/check-dead-code.sh + 暂存区差异/敏感文件核对 |

- 修复业务 bug 时，优先添加能复现根因的最小回归；纯样式/文案不编写只匹配实现字符串的测试。
- 受影响的功能流程、权限和数据一致性比测试数量重要。检查已通过且没有新变更/风险时，转入交付。
- 用户明确限制验证时按其要求执行，并如实说明未验证范围；任何测试都不授权写正式数据。
- 数据库测试先核对 conftest 和连接目标，确认隔离库/schema。连接失败不能改为使用正式数据库。
- 工具缺失优先使用现有本地运行时/venv；需要新增依赖按 AGENTS.md 授权规则，不为验证自动装全局工具。

## 失败如何处理

1. 本次引入或与目标直接相关：定位根因、修复、重跑受影响检查。不得删断言、skip 用例或用 any 隐藏问题。
2. 确认已有且无关：记录失败项与依据（例如修改前同样失败或对照证据），不扩展为全仓修复。
3. 环境受阻：做可执行的静态/替代检查，说明尚未验证的关键路径和所需环境。真实阻塞不等于通过。
4. 无法判断归属：进行最小对照诊断；若关键正确性仍无法确认，明确报告，不能声称安全可发布。

冗余脚本是线索而非完成判据：它会将兼容保留的废弃标记计为问题，部分工具缺失时也可能跳过检查。阅读输出，不把退出码 0 当作所有工具成功；非零时区分新增缺陷、历史问题和有意保留，不要求删除合法兼容代码来凑全绿。清理方式遵循 AGENTS.md。

## 收尾

- 没有开发者工具时，不伪称真机已验；先完成可完成的验证，再列出仅剩的真机检查，不把整项工作都推给用户。
- 已授权提交/推送时继续执行，不在验证后重新问同一个授权问题。未知的关键失败或目标变化需要说明；无关基线问题不自动阻塞已授权的普通提交。
- 只暂存本次相关内容；中文 commit；推送前核对 remote/branch。详见 AGENTS.md，不复制红线表。
- 输出已完成结果、实际检查及必要的剩余项；不以“还可以再测更多”无限延长任务。
