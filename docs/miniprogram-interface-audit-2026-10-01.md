# 小程序接口复核清单（2026-10-01）

## 范围与边界

目标是找齐本轮读取优化的关联问题：请求归属、筛选分页、响应体大小、失败重试、人员目录、请求封装。不是重新审计全部业务规则，也不改页面设计、权限或扣卡口径。

检查范围由当前 `app.json` 固定：管理端 29 个页面、客户端 10 个页面；沿引用递归核对 43 / 13 个脚本，并复核两端 `app.js`，合计 44 / 14 个脚本，包括人员选择、付费表单、协作信息组件及共享课程记录实现。非注册历史页面、归档、设计预览不属于运行入口。两端数据源均保持正式配置，但所有执行检查使用本地源码和模拟请求，未调用正式业务接口。

本报告是审阅结果，**下列待办尚未实施**。此前已完成的客户分页、沟通分页、邀约日期保护、日报日期及来源统一等不重复列为待办。此次只新增报告，不修改业务源码、不提交 Git。

## 三条交叉检查路径

1. 页面与依赖：逐一核对注册入口、引用文件、组件、API 对象方法、动态付费类型工厂。未发现缺文件、JavaScript 语法错误或已引用 API 方法不存在；9 个常规付费类型均有对应获取与分页方法。
2. 请求与后端：核对实际分页、日期参数、人员目录和完整统计是否真的由服务端处理；区分响应裁剪与计算量下降，不能仅凭参数名判断性能。
3. 时序与失败：让旧请求晚于新请求返回，以及让目录读取失败；执行现有页面/组件方法复现问题，不只检查源码字符串。

这些检查不能替代 WXML 全项目编译、真机触摸/键盘测试、真实大数据量或正式服务器耗时验收。

## 固定待办：六类根因

### M1 · 请求结果必须绑定发起时的条件（优先修复）

已复现：

| 入口 | 实际现象 | 位置 |
| --- | --- | --- |
| 服务老师／课程记录的跟进记录 | 已选乙老师，旧响应把列表换回甲老师客户 | `miniprogram/utils/service-teacher-records.js` → `loadFollowUps` |
| 新增课表 | 日期已换到新日期，案主候选名单被旧日期覆盖 | `miniprogram/pages/activity-create/index.js` → `loadDayVisitors` |
| 粗门次卡表单 | 已选乙客户，旧响应显示甲客户的可抵扣课程 | `miniprogram/components/payment-form/index.js` → `_loadCoarseDoorOptions` |
| 邀约客户选择组件 | 搜索词是乙，旧请求返回后候选显示甲 | `miniprogram/components/customer-picker/index.js` → `doSearch` |
| 自定义筛选 | 查询后立即重置，旧结果再次出现，旧条件写回表单 | `miniprogram/pages/custom-analysis/index.js` → `execute` / `onReset` |
| 客户端首页 | 选中 10 月 8 日，旧周请求返回后显示 10 月 1 日分组 | `miniprogram-client/pages/home/index.js` → `_fetchWeekFor` |

同根因关联入口必须一起处理，不再拆成后续“新发现”：

- 编辑课表的 `loadDayVisitors` 与新增课表同构。
- 新增邀约的上次需求／到访目的、协作信息组件的记录及附加内容、课程记录填写弹层：切换客户、记录或关闭后，不能将旧请求提交到新上下文。组件 `loadNotes` 在 loading 时直接跳过新的来源，随后又用当前类别过滤旧来源数据。
- 课程记录填写弹层成功分支已比对 visitId / field，但 catch / finally 未使用相同归属判断；旧失败仍可能关闭新弹层或改变新弹层的加载状态。保留已正确的成功保护，补全同一结果提交约束。
- 付费列表粗门次卡分支的 `loadCoarseDoorData` 直接提交结果，外层序号检查发生在提交之后；应让结果提交统一受请求归属约束。
- 客户详情刷新、沟通记录刷新等固定 ID 入口也要防止较早读取覆盖最新保存后的刷新，不必为此重写整个页面。
- 客户端首次读取、加载更多、按周刷新要共享一致的数据归属，列表追加按 ID 去重；月份圆点更新不得混入当前正文。
- PC 自定义筛选 `execute` 同样无结果归属保护，需同步处理。PC 服务老师跟进列表已有 `useServerPagination` / `isCurrent` 保护，不重复改写。

验收：快速切换日期、老师、客户、筛选；清空搜索；重置查询；关闭再打开弹层；保存后的刷新；退出页面。旧成功、旧失败和旧 finally 均不得改变当前列表、输入内容或加载状态。只增加小型请求归属机制，不引入全站状态框架。

### M2 · 真分页必须包含筛选、完整选项和汇总

- 管理端付费列表调用 `api.list()`，全部类型记录返回后在前端筛选。改为已有分页入口之前，需要后端支持当前创建人、多选子类型等筛选，完整选项与人数不能只从第一页生成。相关位置：`pages/payment/index.js`、`utils/api.js` 项目工厂及对应付费资源路由。全量导出独立保留。
- 信息核对发送 `pageSize: 0`，随后每 16 毫秒扩大 `days.slice(0, shown)`。这是一次下载全部数据后的分批绘制，不是真分页，且反复传输已显示日期。后端 `audit_check.py` 也先核对全部范围再切片，单改为 20 条只减响应体，不能保证减计算量。
- 客户端日期范围入口固定 `page_size=100`，没有读后续页；后端确实最多返回 100 条。超过 100 条会漏活动/日历标记，不是单纯性能问题。
- 客户端活动列表后端先聚合、格式化全部已发布活动，再切页；前端分页本身不能消除全部格式化成本。

验收：首屏只取必要明细；筛选先于分页；统计覆盖完整选择范围；所有历史日期能继续读取；跨页无遗漏或重复；超过 100 条范围仍完整。信息核对不得为提速重新退回“只看最近若干天”。

### M3 · 失败不能伪装为空，也不能把失败标成准备完成（优先修复）

已复现：付费列表姓名目录首次失败后 `_customerSearchReady` 仍为 true；再次调用不请求，姓名搜索一直缺失。`pages/payment/index.js` → `loadCustomerSearchIndex`。模拟连续两次调用，实际读取次数仍为 1。

关联入口：客户详情沟通读取失败直接设置空数组和零计数；付费、标签、人员/组织元数据等读取失败仅关闭 loading 或吞掉异常；客户端交易读取先清空内容，失败后缺少页面内错误状态。现有请求层提示不等于页面结果已经正确。

验收：首次失败显示可重试状态；失败不显示“无记录／零条”的成功结论；重试成功可恢复搜索和选项；旧失败不能覆盖新成功。 optional 装饰图片或非关键使用日志失败不作为阻塞业务的错误。

### M4 · 人员选择目录应按用途轻量化

`customerApi.light(200/1000)` 传 `limit`，但 `backend/app/api/customers.py:list_customers_light` 不接收该参数，实际返回完整可见目录，并遍历到店记录计算 `visit_count`。因此不能说这里被截成 200/1000 人，也不能靠调大 limit 提速。

关联：新增/编辑客户、邀约、课表、付费表单与付费姓名索引。只需姓名/昵称的选择器不应强制承担到店统计成本；完整引流人、老师选项不得改成“当前列表页的人”。

验收：复用现有接口体系，按用途返回必要字段；如增加搜索分页，保留已选人员显示及完整筛选选项；姓名、昵称均能查；客户可见范围与脱敏规则不变。依赖 `visit_count` 的调用保留原语义，不全局删字段。

### M5 · 详情和个人历史拆分读取，保留完整统计

- 管理端客户详情首屏同时取活动、跟进、付费、卡次等历史，再单独取沟通记录。可按 tab 读取明细，轻量汇总先显示；必须保留当前权限和受限详情模式，不能绕开后端范围限制。
- 正常模式的沟通并非后端已经返回后又重复读取；受限参与者模式使用接口提供的沟通内容。优化不能误删正常模式读取。
- 客户端交易、活动、销卡历史一次读全；“我的”也取完整活动记录来做时间线。明细可分页，汇总不能从当前页推算；同源扣卡记录规则不变。
- 编辑课表元数据读取有串行等待，付费详情的组织目录与详情并发但只在详情返回时合成组织名。独立元数据应并行，展示派生值应在两者就绪时都能更新，而不是依赖网络返回顺序。

验收：首屏只等待当前展示必需来源；点击 tab 的内容、计数与现有口径一致；元数据先后返回均显示正确；详情与导出保留完整历史。

### M6 · 请求封装去冗余并覆盖实际旁路

- 管理端 API 导出对象重复定义 `activityThemeApi` / `visitVerificationApi`，前面定义被后面同名项覆盖。当前最终方法存在，不属于已确认功能缺失，但应保留唯一有效定义，降低维护歧义。
- 邀约与付费导出使用页面直接 `wx.downloadFile`，公开图片上传使用独立 `wx.uploadFile`；与普通业务请求的续期、来源标头和错误解析不一致。收敛必要行为，不强行把二进制下载改成 JSON 请求。
- 客户端通知、销卡 GET URL 加当前时间戳，导致同条件在途请求无法合并；相应后端已设置 no-store/no-cache。确认保留刷新语义后使用稳定请求键即可，不增加长时间业务缓存。
- 客户端响应写入续期 token 和处理 401 时未对比发起请求的会话，管理端普通成功续期已有旧 token 比对。客户端需防止旧会话续期/401 更新或清除新登录状态，不能直接复制管理端微信绑定登录流程。
- 管理端/客户端登录态、游客机制和错误处理不能混成一个封装；403/网络错误不清登录，写入、审计日志和心跳不去重。

验收：上传/导出可识别登录失效与无权限；重复读取仅共享在途结果，失败释放、写入失效；重新登录后的旧响应不修改新会话。文件导出来源与操作/使用记录保持正确。

## 收尾规则

先完成 M1 与 M3 的正确性，再处理 M2/M4/M5 的数据量，最后收敛 M6。关联入口在同类根因修复中一次覆盖，不逐页追加待办。

每类以相同验收场景回归；此前已优化页面做最小防回归检查。达到这份清单及必要交互验收后结束本轮，不以“顺便再全站检查一次”为无限扩展理由。新增功能、新数据规模、真机特定行为或生产环境问题单独记录，并明确不属于本轮已经验证的结论。

没有正式网络耗时测试，不能承诺 100 毫秒，也不能承诺软件永远不再出现新问题。当前可确认的是本轮范围、源码证据和上述 7 个模拟复现场景，而不是全部业务无缺陷。
