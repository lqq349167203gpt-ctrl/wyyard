## 范围与结论边界

- 目标：减少重复逻辑和不必要的加载，让后续增加页面更不容易出错，而非单个页面堆缓存。
- 对照 `frontend/src/App.tsx` 路由清单核对；32 个非动态页面已做本地登录态首屏检查，补查下列主要子页。页面能打开不代表所有数据口径与增删改都已验证。
- 浏览器使用本地超级管理员登录态；未覆盖普通角色完整权限矩阵、正式服务器、小程序真机与大数据量压力测试。
- 未新增、修改、删除业务记录，未提交或推送。页面访问会自然产生现有使用统计日志。
- 临时请求计时只记录路径、方法、状态、耗时，不记录载荷、查询参数或凭据；检查后已撤除。原有未提交改动保留。
- 本次续查初期后端未运行，出现 502；恢复本地后端后页面恢复。应与页面自身性能问题分开判断。

## 建议先处理的问题

### 1. 每日报表：旧请求可能覆盖新日期数据（优先）

位置：`frontend/src/pages/daily-report/index.tsx:315-641`。

- 日期切换后，到场人数、邀约、活动、财务/扣卡多组请求分别更新状态，没有过期请求保护。
- 财务 effect 同时依赖日期、客户与活动数据；这些数据先后到达会重复启动同一组请求。
- 旧日期请求若晚返回，仍能写入新日期的页面；日期刚变化时还可能与上一日期的活动数组一起计算。
- 部分请求 `.catch(() => [])` 后继续汇总，失败会表现成少数据或零。

证据级别：源码确认缺少保护；尚未通过人为延迟复现具体错日记录，不据此声称当前报表已算错。

建议：以日期作为同一查询的标识，只有当前请求能提交整组结果；把失败与空数据分开。先修正确性，再考虑用专门的按日读接口替代前端聚合。

### 2. 多处加载失败被当作空数据（优先）

位置：

- `frontend/src/pages/communication-records/index.tsx:60-76`
- `frontend/src/pages/followup-records/index.tsx:25-40`
- `frontend/src/pages/organizations/index.tsx:76-95`
- 每日报表上述 effect。

网络错误或无权限时，部分列表清空或配置列表变为空数组，使用者不易区分“没有内容”和“没有成功取得内容”。组织信息还有内层 catch 后外层再空 catch 的冗余。

建议：复用一致的加载/失败/重试状态；保留旧数据时标记“未更新”，不能悄悄当成本次结果。不把所有空 catch 一次性机械替换，区分可选辅助信息与核心数据。

### 3. 组织/俱乐部：转化分析未查询时沿用旧条数

实测从成交量切至转化分析，下方提示“点查询按当前范围与规则出结果”，上方却仍显示上一页“共 58 条”，导出按钮也可用。

位置：`frontend/src/pages/principal/index.tsx:2288-2296`、`:2370-2418`。

列表主体检查了 `resultTab`，条数和导出可用状态没有使用同一结果归属判断。未点击导出，因此没有验证导出文件内容是否错误。

建议：统一判断结果是否属于当前查询；标题、条数、列表、导出一起使用该判断。保留旧数据以免闪动可以，但不能把它标成新条件的结果。

### 4. 页面权限入口不完整

`frontend/src/App.tsx` 的 `PATH_PERMISSIONS` 缺少 `/config/upsell` 对应 `upsell-config`。

后端 `backend/app/api/upsell_config.py` 已有 `require_page_permission("upsell-config")`，所以目前证据支持的是前端入口校验不一致，不是已证实的数据泄露。

建议：先补齐具体映射；再用一份小型路由描述复用路径、页面权限和导航信息，配自动检查防漏。无需为此重写全站权限系统。

### 5. 共用下拉框的嵌套按钮

位置：`frontend/src/components/select-dropdown.tsx:287-329`。

外层按钮内部又包含多选删除按钮/单选清除按钮。监管信息核对页已在浏览器复现 React 的嵌套 button 警告。

影响：无效交互结构，容易产生焦点、键盘和点击事件问题。当前为客户端应用，不将警告描述为已发生的服务端 hydration 故障。

建议：在共用组件中一次修复语义结构，并检查展开、选中、移除、清空及键盘操作，不逐页复制新的下拉框。

## 性能与简洁度的共性问题

### 重复首屏请求

浏览器捕获多个页面重复请求。`main.tsx` 启用 StrictMode，本地开发会放大 effect 重复执行；不能把开发请求次数直接等同正式环境，也不建议关闭 StrictMode 掩盖问题。

生产也可能存在的重复来源：

- 每日报表单独读取当日邀约，在财务请求组又读一次；客户/活动到达又触发多类付费全量读取。
- 课表的父层和表格层都获取活动类型，案主余额加载还存在按记录反复读取同一天候选集的路径（`activity-batch-table.tsx:599`、`:655`，`daily-activities/index.tsx:2259`）。
- 客户新增/编辑初始化使用 `customerApi.light(true)`，强制绕过现有候选缓存；是否必须刷新应按写入失效规则判断。

建议：先明确每份数据由谁加载；只读候选请求按账号/权限与完整参数复用进行中的请求。保留现有客户候选缓存失效机制，不对写入、导出、操作日志和心跳做无差别去重。

### 非必要全量读取、串行等待

- 组织信息依次等待组织、完整客户、课程类型、可见人员，独立依赖可以并行或按面板需要加载。
- 沟通记录、回访记录、疗愈老师、退费、操作日志等还存在完整客户读取。只需要昵称/身份/候选时应核对后改用轻量来源，不能盲目替换需要详情的场景。
- 沟通与回访仍是全量记录后前端分页；数据增长时首屏与内存成本会增加。
- 每日报表读取多种完整付费项目再筛某一天，应作为后续按范围读取的优先目标。

已核对会员卡无 page 参数接口仍返回完整集合；回访接口也返回完整 records。本轮未发现这两个入口被默认100条截断，不能把全量读取问题误报为截断问题。

### 测量口径

首屏自动化观察包含导航、代码加载和工具调用开销，不能作为精确页面耗时或100毫秒达标证明。请求日志只是单个请求耗时，不是整个页面可用时间。

后续应分别记录：首次进入、再次进入、筛选/翻页、核心数据可用、后台辅助请求完成。以稳定的重复测量和较慢分位数判定改善，不承诺所有页面/所有网络100毫秒完整加载。

## 实施建议

1. 先修结果正确性：日期旧响应、错误当空、结果归属、权限入口遗漏。
2. 再修共用基础：下拉框结构、只读请求在途复用、统一查询状态；复用 `useServerPagination` 和既有 API 层，不新增第二套框架。

验收既看速度也看复杂度：请求减少、依赖清楚、共享规则只维护一处、旧请求不能覆盖、错误可见、新增页面能够沿用现有实现。禁止通过隐藏错误、取消权限校验、截断数据或延长缓存掩盖问题。

## 续查正确性修复（2026-09-30）

- 每日报表导出绑定已加载日期与完整加载状态；切日期或加载失败时禁止导出，避免把旧数据标为新日期。

验证：前端26项定向回归、后端14项定向回归、前端生产构建、修改Python文件检查与差异格式检查通过。后端测试仅使用本机 `wyyard_test` 隔离schema；未写入业务记录。浏览器已确认报表切日期时导出禁用、完成后正常显示、今日排序正常，以及组织列表2次邀约对应同周期2条明细；成交弹窗也按所选客户与统计区间正常显示，列表1笔对应弹窗1笔。普通角色完整权限矩阵和正式环境仍未逐项实测；超过100笔使用隔离回归验证，不通过新增业务数据构造场景。

### 实现如何减少后续重复代码

- 页面菜单、地址、权限和预加载共用 `page-registry.ts`，30个菜单页面对应关系有自动检查。
- 普通记录分页复用 `useServerPagination`，人员目录/配置复用 `useReadResource`，失败展示复用 `LoadError`；未引入第二套请求框架。
- 共享请求只合并进行中的安全读取，不长期保存普通业务结果。有效权限已有独立并发控制，不再被通用复用层干扰强制刷新；回归用例已覆盖此边界。
- 每日报表和全部付费项目收敛读取入口，保留原业务计算及旧接口默认返回方式，不靠加载前100笔或全客户详情拼装列表。

### 验证结果

- 前端36项定向回归通过；最终生产构建通过。既有较大构建块提示仍存在，不等于编译失败，本轮未扩展为打包架构重写。
- 后端92项不同的定向用例通过（原联合89项，加最后3项补充用例）；最后14项完成用例单独通过。相关Python文件静态检查通过。
- 用例覆盖旧接口兼容、可见客户隔离、交易权限拒绝、超过100笔分页、旧响应保护、保存后的强制权限刷新、业务写后版本失效、失败提交不推进版本等。
- 数据库用例使用已核实的 `wyyard_test` 隔离schema；未在业务schema执行清理。浏览器只读取现有记录和候选，未提交退费、销卡或其他业务修改。正常访问仍会产生系统已有的使用统计。
- 本地浏览器核对了客户资料、邀约、课表、组织/俱乐部、付费项目、沟通、回访、落地课程、每日报表、账号权限、疗愈老师、组织信息、退费、销卡以及操作/系统日志。账号权限四组配置齐全后编辑区域出现；退费和销卡候选没有请求错误。
- 临时计时已移除，不留下请求调试输出。没有提交、推送或部署；已有其他改动保留。

### 明确未验证的边界

1. 正式服务器负载、网络延迟和所有普通角色组合未做端到端验收；权限拒绝及隔离已有定向回归，但不能等同于全部角色人工走查。
2. 组织分析复用限制为单进程15秒、最多8组/每组1万行，按账号/权限/日期/业务数据版本隔离；普通系统持久化写入使本进程版本失效。多工作进程之间及绕过系统的外部数据库写入未验证跨进程即时失效。本轮不增加分布式缓存。
3. 管理端/客户端小程序本轮未改源码、未切数据源，旧接口兼容已有检查；不宣称微信真机验收完成。

本轮固定范围到此结束。以后新增页面优先接入上述共享入口与定向回归；新发现的独立需求单独记录，不再回填本轮使结束条件不断变化。
